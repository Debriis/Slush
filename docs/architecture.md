# Architecture

The repository is an npm workspace with frontend and backend packages. Original Expo assets/configuration were moved intact; the old starter source is preserved under frontend/legacy-src and is not routed. All maintained application code is JavaScript/JSX. frontend/app uses Expo Router route files that delegate to features. Auth screens, protected tabs, clan/user detail pages and notifications are separate routes. The new design is dark with purple accents and native safe areas.

Frontend: Supabase Auth owns the session; native token storage uses Expo SecureStore chunks, web uses AsyncStorage/browser storage. AuthProvider restores the session, handles reset links, cleans up AppState/link listeners, and provisions the real database profile via POST /me. TanStack Query owns remote data, pagination, cache and retries. Zustand stores only feed/ranking UI preferences. Forms use local state. Request cancellation, timeouts, JSON validation, friendly errors, retries, and empty states live in shared modules. Invalid configuration renders an explicit setup page. No mock-data fallback exists.

Web uses a client-rendered single-page Expo output, with async routes disabled. This app has no public SEO content and does not need authenticated SSR; this also removes the previous template's server/client hydration mismatch path. Static hosts must rewrite routes to index.html. Reanimated remains installed and Router tabs use fade transitions. No new custom-build-only native modules were added.

Backend: Express verifies every /api bearer token against Supabase Auth. Routes validate all input with Zod strict objects, then call Prisma and shared authorization/scoring services. Public API profiles never expose email or evidence records. Clan operations check membership and role. Clan mutations use a transaction/advisory lock. The API uses Helmet, explicit CORS, bounded JSON bodies, rate limiting, and redacted errors. Never log raw Auth/database errors or request credentials. Live URLs and database credentials are not included in app source.

Database: foreign keys, uniqueness and indexes protect relationships, accepted problems and XP transactions. All client-facing table writes are revoked; Realtime can SELECT only permitted chat/post/notification rows via RLS. Backend SQL uses Prisma tagged parameters; scope and metric are validated enums. The frontend cannot create verified activity, XP or rank.

Scoring: verified activities are inserted only by trusted independent claim review. The accepted-problem uniqueness constraint prevents repeat XP even across submissions. A single transaction awards XP, updates local-day summaries/streak storage, awards the first-verified badge and notifies the user. Streak display recalculates relative to today so stale stored streaks do not persist forever. Time zones are locked after verified activity; changing one requires a future administrator migration/review workflow. Rankings use PostgreSQL RANK over authoritative transactions; UTC weekly/monthly windows avoid reset jobs. Clan scores count only activity since the current membership began.

Realtime: subscriptions react to inserts and invalidate Query caches, with channel cleanup on unmount. Private chat content requires current membership via a SECURITY DEFINER membership check with fixed empty search_path. Notifications are limited to auth.uid(). Failed subscription status is visible and manual refresh remains available.

Platform adapters: a registry rejects unauthorized implementations. No automatic adapter is registered, no scraper exists, and LeetCode usernames remain self-reported. Evidence review is a legitimate operator workflow only when genuine evidence can be verified; it is not an automatic integration. Scheduled scraping/import/reset jobs are intentionally absent. Time-windowed SQL eliminates artificial XP resets.
